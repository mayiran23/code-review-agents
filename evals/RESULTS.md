## 第 2 轮 · 2026-10-31

架构改造：单 Agent 拆成 `security` / `performance` / `style` 三路并行子图，中间加 `merge` 归并节点。

```
应报 17 个 | 报对 16 个 | 召回率 94.1%
干净样本误报 1 个
```

### 与第 1 轮对比

| 指标 | 第 1 轮（单 Agent） | 第 2 轮（三路并行） |
|---|---|---|
| 召回率 | 82.4%（14/17） | **94.1%（16/17）** |
| 对照误报 | 2 | 1 |

**提升 11.7 个百分点。**

### 中途踩的坑：责任分散

三路并行的**第一版**（提示词写「不要报其他类别 —— 有专门的审查员」）召回仍是 **82.4%，一点没涨**。

反直觉的现象：同一份 `sample_22`，单 Agent 报 5 条，三路并行只报 3 条。

**原因**：三个 Agent 都判断"这问题不归我"，跨类别的问题谁都不报。这在多智能体系统里叫**责任分散**。

**修正**：提示词从「不要报」改成「**优先不报，但 P0/P1 仍可越界报出**」，并把理由写进提示词：

> 重复的意见会在归并阶段去重，漏掉的不会有人补。

因为 `merge` 会按「文件 × 行号」去重，**重复的代价是零，漏报的代价是无限**。改完召回从 82.4% 涨到 94.1%。

### 剩余漏报（1 个）

| 样本 | 期望 | 原因 |
|---|---|---|
| sample_24 | L2「税率」 | `tax_rate` 传 13 还是 0.13，需业务约定，代码里看不出来 |

### 误报归零过程中修的样本

第 2 轮第一次跑出 **6 条误报**，逐条核查后发现 3 条是我样本里的真实缺陷：

| 样本 | 模型报的 | 核查结论 |
|---|---|---|
| sample_14 / 23 | `SELECT *` 多传无用列 | **确实是缺陷** |
| sample_16 | `path` 未校验直接 `open()`，可读任意文件 | **确实是缺陷** |

修完这 6 个对照样本后，误报降到 1 条（经核查仍是真实缺陷：`affected == 0` 时没记录失败日志）。

## 三个值得记录的观察

### 1. 模型报得比标准答案更全

`sample_22` 只标了 2 个坑，模型报了 **5 条**：

| 模型意见 | 我是否预料到 |
|---|---|
| L4 Webhook URL 硬编码，含可滥用的凭证式 token | ✗ 没想到 |
| L9 requests.post 未设 timeout，下游挂起会阻塞线程 | ✗ 没想到 |
| L9 未检查返回状态、未捕获异常，失败静默吞掉且无日志 | ✗ 没想到 |
| L9 user 对象（含密码/手机号）原样外发第三方 | ✓ 这条是标的 |
| L8 先写库后发 webhook，无事务/补偿 | ✗ 没想到 |

**这是它不是"套模板"的最有力证据。**

### 2. 同一批样本跑两次，结果会变

`sample_12`（变量名 `count` 实为名字列表）：

- 第 1 次：报了 P3 L5「变量名 count 与含义严重不符」→ **命中**
- 第 2 次：只报了 P1 L6「N+1 查询」→ **漏报**

`temperature=0` 不等于完全确定（GPU 浮点误差、batch 顺序都会影响）。

**结论：单次评估不可靠，关键结论需要跑 2-3 次取稳定值，或扩大样本量。**

### 3. 漏报集中在"需要外部上下文"的问题

| 样本 | 漏报原因 |
|---|---|
| sample_09 | `LIKE '%x%'` 是否索引失效，取决于该字段有没有索引 —— 看不到 schema |
| sample_24 | `tax_rate` 传 13 还是 0.13，取决于调用方约定 —— 看不到业务规则 |

**模型只看 diff，看不到表结构和业务约定，这两类是它的能力天花板。**

## 能力边界

| 它擅长的 | 它会漏的 |
|---|---|
| 代码本身能看出来的问题 | 需要代码之外信息的问题 |
| SQL 注入、硬编码密钥、路径穿越、异常被吞、N+1、缺分页 | 索引是否存在、字段语义、业务规则、跨文件影响 |
| 常常比人工标注更全面 | 对"片段缺依赖"不敏感（偶尔报未导入的类） |

**优化方向：补 schema 上下文（表结构、索引、字段说明），而不是继续调提示词。**

---

## 判定规则的已知局限

1. **关键词匹配本质是"用字符串代替语义"**，措辞一变就判漏。实例：模型写「`except Exception: pass` 异常被吞掉」，我标的 keyword 是「异常」，判定失败；改成「吞」才算命中。
2. **不检查 category / severity 是否一致**，模型把 P0 报成 P2 也算命中。
3. **否定句会误判为命中**：若模型说"不存在注入风险"，含"注入"二字会被算对。
4. 未来改进方向：同义词组 + LLM-as-judge 复核。
